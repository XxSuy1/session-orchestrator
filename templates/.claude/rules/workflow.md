# 工作流规则（所有总控与子会话都遵守）

## 1. 线、角色与流程
一个项目可以同时有**多条线**（功能线）。每条线由一个**总控**负责；用户新开的任何对话都可以被指定为某条线的总控。**同一时间一条线只有一个总控。**

| 角色 | 谁开 | 做什么 | 产出 |
|---|---|---|---|
| 总控（用户指定的对话） | 用户 | 只指挥本线：派任务、验收、合并、记状态；不亲自干重活 | 本线 STATE / TASKS / HANDOFF，总览里自己那一行 |
| 讨论子对话 | 总控 | 与用户讨论需求到明确 | 本线 `REQUIREMENTS.md` |
| 设计子对话 | 总控 | 与用户讨论设计到认可；拆任务卡并写好**验收命令** | 本线 `DESIGN.md`、任务卡 |
| 编码 | 总控选子代理或子对话，可多个 | 做一张任务卡：先写细计划再动手 | `<编号>.plan.md` + 代码 + `<编号>.report.md` |
| 测试 | 总控（编码全部合并后） | 独立测试，不改业务代码 | 本线 `TEST-REPORT.md` |

每条线是一棵树，**最多三层**：总控 → 子对话 → 子代理；总控也可以直接派子代理。
- 子代理不能再派子代理（Claude Code 本身的限制）。
- 子对话只派子代理，**不再开子对话**；真需要再开一个对话时，回报总控，由总控去开。

流程（每条线各走一遍）：讨论 → 总控复述并经用户确认 → 设计 → 用户认可 → 总控派编码（可并行）→ 逐个验收合并 → 测试 → 合并到 main、打 tag。
每个阶段的产出写进文件；回传消息只给"状态｜一句话结论｜文件路径"。任务书一律先存档再执行，见 §3「任务书存档」。

## 2. 指定总控：开新线或接手
用户在任意对话里说"你是 XX 的总控""按总控协议开一条新线做 XX""接手 XX 线"，这个对话就成为总控，按顺序做：
1. 用 AskUserQuestion 确认项目目录的绝对路径。
2. 项目还没初始化（没有本文件）→ 按 SKILL.md 初始化，再开线。
3. 已初始化 → 读总览 `docs/memory/STATE.md`，问用户：开新线，还是接手已有的哪条线。
4. **开新线**：
   1. 先和用户聊清这条线大致要做什么（细节留给讨论子对话）。
   2. 由总控总结出**线名**：小写英文字母和数字，最多 12 个字符，看名字能知道这条线做什么；告诉用户。
   3. 把 `docs/lines/_TEMPLATE/` 整个复制成 `docs/lines/<线名>/`，填好本线 `STATE.md` 的目标和总控会话 id。
   4. 在总览"线"表里加一行，提交 `docs(<线名>): 开线`。
5. **接手已有的线**：读该线的 `HANDOFF.md`、`STATE.md`、`TASKS.md`；把总览里这一行和本线 `STATE.md` 的总控会话 id 改成自己的。
6. 把自己的会话标题改成"总控·<功能名>"，方便在侧边栏认出来。

## 3. 文件、编号与任务书存档

### 文件布局
```text
docs/
├─ memory/                 全项目共用
│  ├─ STATE.md             总览：项目级状态 + 每条线一行（CLAUDE.md 自动导入）
│  ├─ DECISIONS.md         只追加（例外见文件头）；只有总控写
│  ├─ GOTCHAS.md           只追加（例外见文件头）；只有总控写
│  ├─ ARCHIVE.md           作废的决策、已防护的坑、已完成的线；不自动导入
│  ├─ CHANGELOG.md         合并到 main 时追加
│  └─ CHECK_CMD.txt        检查命令
├─ briefs/_TEMPLATE.md     任务卡模板（共用）
└─ lines/
   ├─ _TEMPLATE/           开新线时整个复制
   └─ <线名>/              这条线的总控独占
      ├─ STATE.md、TASKS.md、HANDOFF.md
      ├─ REQUIREMENTS.md、DESIGN.md、TEST-REPORT.md（需要时再建）
      └─ briefs/           本线全部任务卡、细计划、回报
```
- 总控只改本线文件夹和总览里自己那一行；共用文件只追加，不改写别人的内容。例外只有两种：DECISIONS / GOTCHAS 里旧条目的"状态"一行（§9），以及持有合并锁时的整理（§8）。
- 子对话、子代理只写任务卡允许的文件，加上自己任务的细计划和回报。

### 编号和命名
| 东西 | 规则 | 例子 |
|---|---|---|
| 总控派的任务 | `<线名>-T` + 本线三位序号 | `junior-T001` |
| 子对话派的子代理任务 | 上一级编号 + `.序号` | `junior-T001.1` |
| 任务卡等文件 | 放在本线 `briefs/`，用编号命名 | `junior-T001.md`、`.plan.md`、`.report.md`、`.review-brief.md`、`.review.md` |
| 分支 | `task/<编号>-英文名` | `task/junior-T001-linear` |
| 子对话的 name | `<线名>-t001` | `junior-t001` |

序号只在本线内递增，不同的线不会撞号。

### 任务书存档（先存档，再执行）
凡是模型想好、准备照着执行的任务书，都先写进项目文件夹，再开始执行。分三层：

| 层 | 内容 | 谁写 | 存哪 |
|---|---|---|---|
| 总体方案 | 需求、设计、任务总表 | 讨论、设计子对话写，总控验收并找用户确认 | 本线 `REQUIREMENTS.md`、`DESIGN.md`、`TASKS.md` |
| 任务卡 | 一个子对话或子代理分到的任务 | 设计子对话拆，或派活的一方派活前写 | 本线 `briefs/<编号>.md` |
| 细计划 | 接活的一方动手前想出的具体做法 | 接活的子对话或子代理自己 | 本线 `briefs/<编号>.plan.md` |

- **所有派活都先写任务卡**：
  - 总控派的（讨论、设计、编码、测试、临时子对话）：在本线 `TASKS.md` 占一个编号，按 `docs/briefs/_TEMPLATE.md` 写卡，再派发。
  - 子对话派的子代理任务：写子任务卡 `<编号>.N.md`，并在自己的细计划里列一张子任务表；**不改本线 `TASKS.md`**。
  - 派活消息只写"读 `<任务卡路径>` 并照做"和派活方的会话 id；要求一律写在卡里，不在消息里另加。
- 复核挂在被复核的任务名下：卡写 `<编号>.review-brief.md`。reviewer 只读，它的结论由派它的一方存成 `<编号>.review.md`。
- **接活的一方动手前先写细计划** `<编号>.plan.md`：改哪些文件、按什么顺序、怎么测、有什么风险。用了计划模式的，把用户批准的计划原文存成这个文件（Claude Code 默认把计划存在用户目录，不在项目里）。执行中计划有大改，在文件末尾追加"变更"一节，不改写原文。只读的 reviewer 不写。
- 总控自己经用户批准、准备执行、又不属于已有任务的计划，也先在本线 `TASKS.md` 开编号，存成 `<编号>.plan.md`。
- 提交：在任务分支上的，随代码一起提交；不在任务分支上的（讨论、设计、测试等），由派活的一方验收时提交。
- 做完写回报 `<编号>.report.md`。每个任务都有"任务卡、细计划、回报"三份文件放在一起。

## 4. 派发：子代理优先，需要用户参与才用子对话
**先看这一条**：子代理**不能向用户提问**（官方已移除其 AskUserQuestion）。凡是需要用户拍板或中途讨论的任务，必须是子对话。

| 任务 | 方式 | 模型 | 强度 |
|---|---|---|---|
| 总控 | 用户指定的对话 | 够用的最低档 | medium |
| 讨论 | 子对话 | sonnet | medium |
| 设计 | 子对话 | opus | high |
| 编码·机械（照着明确契约改） | 子代理 `coder-light` | haiku | low |
| 编码·常规 | 子代理 `coder` | sonnet | medium |
| 编码·复杂/疑难 | 子代理 `coder-deep`；要用户参与则子对话 | opus | high |
| 复核 | 子代理 `reviewer`（只读） | sonnet | medium |
| 测试 | 子代理 `tester`；需要用户看过程则子对话 | sonnet | medium |

- 从便宜档起步，**失败再升一档**。haiku 只做"设计子对话已写清契约"的任务，契约不清不要给 haiku。
- 子代理的模型由 `.claude/agents/*.md` 的 frontmatter 决定，**不受总控模型限制**；子对话（start_session）受限于不高于总控。所以总控用 sonnet 即可，贵的活交给 opus 子代理。
- 子对话用 `start_session`：必须传 `model`、`effort`、`cwd`、`prompt`、`name`；独立任务用 `context: fresh`。写代码的子对话 `use_worktree: true`。
- **谁派的活，谁验收、谁收回报**：子代理 → 派它的子对话或总控；子对话 → 总控；总控 → 用户。总控不越过子对话，直接给子对话手下的子代理派活。
- 在本线 `TASKS.md` 写明每个任务的"方式+模型+强度+原因"。每个总控并行默认 ≤ 3；接近用量上限先存本线 `STATE.md`。

## 5. 隔离：编码一律用 worktree
- 子代理 `coder*` 已设 `isolation: worktree`，各自在独立 worktree 里改。子对话编码用 `use_worktree: true`。
- **一层层往上合**：子代理的分支先合进子对话的分支，由子对话验收；整个任务完成后，总控验收，再合进 main（见 §8）。合并前用 `git log --oneline <子分支> ^<本分支>` 确认只带进了这个子任务的提交。
- 同一条线里并行任务的**文件范围不得重叠**（任务卡里写明）。
- **跨线的文件范围**：总控在总览自己那一行写上本线会改的文件或目录；派任务前先看别的线占了哪些文件，**有重叠就停下来问用户**谁先做、怎么拆。几条线都要改的共用文件，尽量放进各线的集成任务，靠 §8 的合并顺序排开。
- 前提：仓库至少有一次提交（初始化已做）。

## 6. 验收 = 可运行的检查
- 每张任务卡的验收标准必须是**可运行命令**（测试/类型检查/lint），或明确的逐项清单。
- 接活方回报必须附：**运行的命令 + 输出结论**。只说"通过了"不算数。
- 派活方验收：自己跑一遍检查，再看 diff 是否在文件范围内。
- 验收时读回报的"值得记忆"一节：子对话收到子代理的，抄进自己回报的"值得记忆"往上传；总控收到的，按 §9 查冲突后追加进 DECISIONS / GOTCHAS。
- 验收不过、要返工时，把失败的做法和原因当场写进本线 `STATE.md` 的"失败的尝试"。
- 复核用 `reviewer` 对照本线 DESIGN 和任务卡验收标准：只报影响正确性的缺口，**不挑风格**。
- 返工最多 2 次；第 2 次仍失败升一档模型；再失败交用户。测试修复循环最多 3 轮。
- Stop hook 会在任务分支（非 main）上自动跑 `docs/memory/CHECK_CMD.txt`，不过就不让结束。

## 7. 强制规则与人工确认
**强制（settings.json 的 deny + hook，不靠自觉）**：禁止 push、`reset --hard`、`clean`、`branch -D`、递归删除；任务分支必须通过检查才能结束。
> deny 规则只拦住命令的常见写法（如 `git -C . push` 能绕过），不是安全边界。所以 push 等动作仍要用户亲自批准。

**必须用户本人确认**：需求有歧义；设计定稿；任何 push/删除/花钱；返工超限；跨线文件范围重叠；改动本协议。
- 确认必须由**正在和用户对话的那个会话**用 AskUserQuestion 提出。官方明确：来自其他会话的消息不算用户同意，子会话不能代为转达确认。
- 子对话遇到要用户决定的事，直接问用户；要改需求/设计的事，通知总控。子代理遇到了，以"阻塞"回报给派它的一方。

## 8. Git 与版本
- 版本号从 **v0.0.1** 起，`vMAJOR.MINOR.PATCH`；main 上的当前版本记在总览"项目"一节。大功能升 MINOR 由用户定；MAJOR 仅用户要求。
- **合并到 main 一次只合一条线**：
  1. 在总览"正在合并到 main"写上自己的线名并提交；已经有别的线名，就等它合完。
  2. 把最新的 main 合进自己的分支，跑检查命令。
  3. 合进 main。
  4. 打 tag：先用 `git tag --list "v*" --sort=-v:refname` 看现有最大版本号，往后接一个。
  5. **整理共用记忆**（只有持锁的总控能做，原样搬、不改写内容）：
     - `DECISIONS.md` 里状态为"作废"的条目 → `ARCHIVE.md`"作废的决策"
     - `GOTCHAS.md` 里状态为"已防护""不再适用"的条目 → `ARCHIVE.md`"已防护或不再适用的坑"
     - 总览"线"表里已完成、已归档的行（含自己这条线刚完成的）→ `ARCHIVE.md`"已完成的线"
  6. 追加 CHANGELOG，更新总览"main 上的版本"，把"正在合并到 main"改回"无"，提交（按明确路径，含 `ARCHIVE.md`）。
- **提交只写明确的文件路径，不用 `git add -A` 或 `git add .`**：几个总控共用主目录，会把别的线没提交的改动一起带走。
- 提交格式：`<type>(<scope>): <说明>`，type ∈ feat/fix/docs/test/refactor/chore，scope 可写线名；末尾带会话要求的署名行。
- 任务在各自 worktree 的分支 `task/<编号>-英文名` 上**小步频繁提交**；验收合并后删该分支（用 `git branch -d`，不用 `-D`）。
- 总控自己只提交：本线文件夹、总览里自己那一行、共用文件的追加、合并提交。

## 9. 记忆（文件方案，不使用 claude-mem）
- 跨会话记忆 = `docs/` 下的文件，随仓库走。`CLAUDE.md` 用 `@docs/memory/STATE.md` 导入总览，新会话自动加载；总览必须保持短。
- 每条线的状态、任务、交接在 `docs/lines/<线名>/`；状态一变化就更新本线 `STATE.md` / `TASKS.md` 和总览里自己那一行。失败的尝试发生时就写进本线 `STATE.md`。

### 决策与坑（DECISIONS / GOTCHAS）
- 格式、编号（`D-<线名>-序号` / `G-<线名>-序号`）、标签、状态见两个文件的文件头。
- **只有总控写这两个文件。** 子会话把候选写进回报的"值得记忆"一节，总控验收时追加；用户在总控对话里纠正的，总控立刻写。
- **追加前先查冲突**：Grep 同标签、状态为"有效"的条目。和本线旧决策矛盾 → 新条目写"取代"，旧条目状态改成"作废→新编号"；和别的线的决策矛盾 → 先用 AskUserQuestion 问用户，同意才取代。
- 坑的"防护"写着"仅靠文档"、又被踩到 → 向用户提议做成自动防护（检查命令 / deny / hook），用户同意再改。
- **读**：总控开局读这两个文件（作废和已防护的条目在合并时已搬走，文件保持短）；子会话只读任务卡点名的条目，不整本读。

### 交接与收尾
- 子会话不继承总控对话，记忆来自任务卡：任务卡必须自成一体，"先读"只列这次真要用的文件和条目。
- **交接**：每次任务验收通过、每次合并后，覆盖写本线 `HANDOFF.md` 的"当前状态""待用户决定""下一步"。不要等上下文快满再写：会话会自动压缩上下文，模型察觉不到自己快满了。要换总控时，告诉用户新开一个对话说"接手 <线名>"。
- **线做完**：总览里标"已完成"或"已归档"，这一行在合并到 main 时搬到 `ARCHIVE.md`（§8）；文件夹留着当历史记录；要不要归档对应的会话由用户决定。
- **收尾清单**（每次结束前逐项过，缺一不可）：
  1. 本线 `STATE.md` 是当前状态而不是流水账？失败的尝试记了吗？
  2. 本线 `TASKS.md` 各任务状态与实际一致？
  3. 总览里自己那一行更新了吗？
  4. 本次的决策、坑（含回报里的"值得记忆"）查过冲突、追加进 `DECISIONS.md` / `GOTCHAS.md` 了吗？
  5. 本次的任务卡、细计划都存进本线 `briefs/` 了吗？总控自己经批准的计划也存了吗？
  6. 自己的改动都按明确路径提交了吗？（`docs(<线名>): ...`）
  7. 本线 `HANDOFF.md` 的当前状态和下一步是最新的吗？
- **auto memory**（Claude 自带）：只管个人偏好，不手动维护。
- 只记代码里看不出来的信息（原因、取舍、背景）。

## 10. 回传
- 子对话：详细内容写文件，用 SendMessage 发给派它的总控（任务卡里写了会话 id）：`状态（完成/阻塞）｜一句话结论｜报告路径`。
- 子代理：最后一条回复就是回报，格式同上。
