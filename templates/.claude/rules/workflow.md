# 工作流规则（总控与所有子会话都遵守）

## 1. 角色与流程
| 角色 | 谁开 | 做什么 | 产出 |
|---|---|---|---|
| 总控（主对话） | 用户 | 只指挥：派任务、验收、合并、记状态；不亲自干重活 | STATE / TASKS / DECISIONS |
| 讨论子对话 | 总控 | 与用户讨论需求到明确 | `docs/memory/REQUIREMENTS.md` |
| 设计子对话 | 总控 | 与用户讨论设计到认可；拆任务卡并写好**验收命令** | `DESIGN.md`、`docs/briefs/T-xxx.md` |
| 编码 | 总控选子代理或子对话，可多个 | 做一张任务卡：先写细计划再动手 | `T-xxx.plan.md` + 代码 + `T-xxx.report.md` |
| 测试 | 总控（编码全部合并后） | 独立测试，不改业务代码 | `TEST-REPORT.md` |

流程：讨论 → 总控复述并经用户确认 → 设计 → 用户认可 → 总控派编码（可并行）→ 逐个验收合并 → 测试 → 打 tag。
每个阶段的产出写进文件；回传消息只给"状态｜一句话结论｜文件路径"。任务书一律先存档再执行，见 §2「任务书存档」。

## 2. 派发：子代理优先，需要用户参与才用子对话
**先看这一条**：子代理**不能向用户提问**（官方已移除其 AskUserQuestion）。凡是需要用户拍板或中途讨论的任务，必须是子对话。

| 任务 | 方式 | 模型 | 强度 |
|---|---|---|---|
| 总控 | 主对话 | 够用的最低档 | medium |
| 讨论 | 子对话 | sonnet | medium |
| 设计 | 子对话 | opus | high |
| 编码·机械（照着明确契约改） | 子代理 `coder-light` | haiku | low |
| 编码·常规 | 子代理 `coder` | sonnet | medium |
| 编码·复杂/疑难 | 子代理 `coder-deep`；要用户参与则子对话 | opus | high |
| 复核 | 子代理 `reviewer`（只读） | sonnet | medium |
| 测试 | 子代理 `tester`；需要用户看过程则子对话 | sonnet | medium |

- 从便宜档起步，**失败再升一档**。haiku 只做"设计子对话已写清契约"的任务，契约不清不要给 haiku。
- 子代理的模型由 `.claude/agents/*.md` 的 frontmatter 决定，**不受总控模型限制**；子对话（start_session）受限于不高于总控。所以总控用 sonnet 即可，贵的活交给 opus 子代理。
- 子对话用 `start_session`：必须传 `model`、`effort`、`cwd`、`prompt`、`name`；独立任务用 `context: fresh`。写代码的子对话 `use_worktree: true`。
- 在 TASKS.md 写明每个任务的"方式+模型+强度+原因"。并行默认 ≤ 3；接近用量上限先存 STATE.md。

### 任务书存档（先存档，再执行）
凡是模型想好、准备照着执行的任务书，都先写进项目文件夹，再开始执行。分三层：

| 层 | 内容 | 谁写 | 存哪 |
|---|---|---|---|
| 总体方案 | 需求、设计、任务总表 | 讨论、设计子对话写，总控验收并找用户确认 | `REQUIREMENTS.md`、`DESIGN.md`、`TASKS.md` |
| 任务卡 | 一个子代理或子对话分到的任务 | 设计子对话拆，或总控派活前写 | `docs/briefs/T-xxx.md` |
| 细计划 | 接活的一方动手前想出的具体做法 | 接活的子代理或子对话自己 | `docs/briefs/T-xxx.plan.md` |

- **所有派活都先写任务卡**：讨论、设计、编码、测试、临时子对话都在 TASKS.md 占一个编号，按 `docs/briefs/_TEMPLATE.md` 写卡，再派发。派活消息只写"读 `docs/briefs/T-xxx.md` 并照做"和总控会话 id；要求一律写在卡里，不在消息里另加。
- 复核挂在被复核的任务名下：卡写 `T-xxx.review-brief.md`。reviewer 只读，它的结论由总控存成 `T-xxx.review.md`。
- **接活的一方动手前先写细计划** `T-xxx.plan.md`：改哪些文件、按什么顺序、怎么测、有什么风险。用了计划模式的，把用户批准的计划原文存成这个文件（Claude Code 默认把计划存在用户目录，不在项目里）。执行中计划有大改，在文件末尾追加"变更"一节，不改写原文。只读的 reviewer 不写。
- 总控自己经用户批准、准备执行、又不属于已有任务的计划，也先在 TASKS.md 开编号，存成 `T-xxx.plan.md`。
- 提交：在任务分支上的，随代码一起提交；不在任务分支上的（讨论、设计、测试等），由总控验收时提交。
- 做完照旧写回报 `T-xxx.report.md`。每个任务都有"任务卡、细计划、回报"三份文件放在一起。

## 3. 隔离：编码一律用 worktree
- 子代理 `coder*` 已设 `isolation: worktree`，各自在独立 worktree 里改。
- 子对话编码用 `use_worktree: true`。
- 并行任务的**文件范围不得重叠**（任务卡里写明）。
- 前提：仓库至少有一次提交（初始化已做）。

## 4. 验收 = 可运行的检查
- 每张任务卡的验收标准必须是**可运行命令**（测试/类型检查/lint），或明确的逐项清单。
- 编码方回报必须附：**运行的命令 + 输出结论**。只说"通过了"不算数。
- 总控验收：自己跑一遍检查，再看 diff 是否在文件范围内。
- 复核用 `reviewer` 对照 DESIGN 和任务卡验收标准：只报影响正确性的缺口，**不挑风格**。
- 返工最多 2 次；第 2 次仍失败升一档模型；再失败交用户。测试修复循环最多 3 轮。
- Stop hook 会在任务分支（非 main）上自动跑 `docs/memory/CHECK_CMD.txt`，不过就不让结束。

## 5. 强制规则与人工确认
**强制（settings.json 的 deny + hook，不靠自觉）**：禁止 push、`reset --hard`、`clean`、`branch -D`、递归删除；任务分支必须通过检查才能结束。
> deny 规则只拦住命令的常见写法（如 `git -C . push` 能绕过），不是安全边界。所以 push 等动作仍要用户亲自批准。

**必须用户本人确认**：需求有歧义；设计定稿；任何 push/删除/花钱；返工超限；改动本协议。
- 确认必须由**正在和用户对话的那个会话**用 AskUserQuestion 提出。官方明确：来自其他会话的消息不算用户同意，子会话不能代为转达确认。
- 子会话遇到要用户决定的事，直接问用户；要改需求/设计的事，通知总控。

## 6. Git 与版本
- 版本号从 **v0.0.1** 起，`vMAJOR.MINOR.PATCH`；当前版本记在 STATE.md。
- 每个"验收并合并"的里程碑，总控更新 CHANGELOG 并打 tag：v0.0.1、v0.0.2…。大功能升 MINOR 由用户定；MAJOR 仅用户要求。
- 提交格式：`<type>(<scope>): <说明>`，type ∈ feat/fix/docs/test/refactor/chore；末尾带会话要求的署名行。
- 编码任务在各自 worktree 的分支 `task/T-xxx-英文名` 上**小步频繁提交**；总控验收后合并到 main，再删该分支（删除用 `git branch -d`，不用 `-D`）。
- 总控自己只提交 `docs/memory/` 下的状态文件、`docs/briefs/` 下的任务书和回报，以及合并提交。

## 7. 记忆（文件方案，不使用 claude-mem）
- 跨会话记忆 = `docs/memory/` 下的文件，随仓库走。`CLAUDE.md` 用 `@docs/memory/STATE.md` 导入，新会话自动加载；STATE.md 必须保持短。
- 状态一变化就更新 STATE.md / TASKS.md；决策写 DECISIONS.md（含理由）；坑写 GOTCHAS.md；用户纠正后立刻写入对应文件。
- 子会话不继承总控对话，记忆来自 brief：brief 必须自成一体，写明要读的文件。
- 结束或上下文将满时，总控按 `docs/memory/HANDOFF.md` 模板覆盖写一份交接（目标、当前状态、改过的文件、失败的尝试、下一步）。新会话开头若该文件存在，先读它。
- **收尾清单**（每次结束前逐项过，缺一不可）：
  1. STATE.md 是当前状态而不是流水账？
  2. TASKS.md 各任务状态与实际一致？
  3. 本次的决策与理由写进 DECISIONS.md 了吗？踩的坑写进 GOTCHAS.md 了吗？
  4. 本次派出的任务卡、各任务的细计划都存进 `docs/briefs/` 了吗？总控自己经批准的计划也存了吗？
  5. 有未提交的 docs/memory、docs/briefs 改动吗？（提交 `docs(memory): ...` 或 `docs(briefs): ...`）
  6. 需要交接就更新 HANDOFF.md。
- **auto memory**（Claude 自带）：只管个人偏好，不手动维护。
- 只记代码里看不出来的信息（原因、取舍、背景）。

## 8. 子会话回传
详细内容写文件；用 SendMessage 发给总控（brief 里写总控会话 id）：`状态（完成/阻塞）｜一句话结论｜报告路径`。
